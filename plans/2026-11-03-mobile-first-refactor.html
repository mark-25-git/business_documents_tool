The plan in simple words

Turn the long desktop form into a focused mobile workspace. Keep familiar invoice fields, larger touch controls, and a Save action within reach. Desktop users still get the editor and preview side by side.

One document, two views

Open directly into the editor. Use Edit / Preview to switch views on phones without losing input or scroll position. Use a Documents button to find saved work in a full-height searchable sheet.

Why the current layout needs work
  • Observed at 390 × 844: the toolbar wraps, search text clips, and five document-type buttons occupy three rows.
  • Source evidence: the main form uses 32px inner padding, 14px inputs, and a 12-column item row even on narrow screens.
  • The PDF viewer is always mounted at 900px tall. On phones it sits after the entire form.
  • Several fields rely on placeholders; small icon actions and custom dropdown rows need stronger touch and keyboard behavior.
  • The active editor is inline in app/page.tsx. components/LineItemsEditor.tsx is not imported there and uses different currency formatting. Refactor the active flow first.

Success criteria

  • At 320, 390, and 430px wide, the editor has no sideways page scroll or clipped controls.
  • People can find a customer, add items, adjust charges, save, reopen, and download using touch.
  • Every editable field has a persistent label. Phone inputs use at least 16px text, and touch actions have at least 44px targets.
  • Switching Edit and Preview, rotating the phone, and opening search keep the current draft intact.
  • Save cannot run twice. Failed requests keep input, explain the error, and allow retry.
  • Existing Google Sheets payloads, document numbers, MYR totals, billing/shipping snapshots, tax storage, and saved-document rules remain compatible.
  • Desktop keeps a useful two-pane layout. PDF page size, branding, content, and downloaded filenames stay consistent.
  • Keyboard, screen reader labels, zoom, focus return, loading/empty/error states, and reduced motion work.

Real iPhone Safari and Android Chrome checks are required before calling the mobile work complete. Desktop viewport testing cannot prove keyboard, safe-area, or download behavior on a phone.

Implementation plan for reference

Scope: a responsive mobile web app using the existing Next.js stack and Google Sheets backend. No new backend, native wrapper, or dependency overhaul. Installable PWA support is a separate follow-up; do not add offline invoice storage or a service worker in this refactor.

1. Separate screen layout from document behavior

Extract the editor state and handlers into a focused useDocumentEditor hook. Keep a single draft shared by mobile and desktop views. Extract customer, metadata, items, charges, totals, document search, and preview components.

Reuse current API calls and payload mapping. Keep ?doc= loading, manual numbering, revisions, temporary customers, master-profile opt-in, soft cancellation/recovery, and existing Save/Download rules. Add a leave-with-unsaved-changes check for Start new and loading another document. No silent autosave.

Check: capture representative payload and PDF baselines before layout work. Verify existing create, reopen, update, cancel, and recover flows against controlled fixtures or an explicitly designated test sheet.

2. Apply Still Balanced at the shared controls

Map canonical tokens into app/globals.css and tailwind.config.ts. Update the existing input, textarea, button, badge, card, dropdown, and confirmation components. Do not maintain two competing themes.

  • Use system font throughout the app, blue #0066cc, neutral surfaces, 18px cards, 12px fields, pill buttons, and circular icon actions.
  • Use 58px floating-label fields. Keep labels inside the border in empty, focused, filled, autofilled, disabled, and error states. Search uses the same pattern. Textarea resting labels align with single-line fields.
  • Text-field focus changes the border and interior label only. Keep visible keyboard focus on actions and selection controls. Use sentence case.
  • Add the shared numeric wheel guard without blurring fields or blocking page scrolling and zoom. Preserve zero, decimal entry, blank editing, and valid negative discount prices.
  • Use the approved loading-fill action button for Save and PDF generation. Use neutral toasts with semantic icons and inline errors linked to fields.

Check: validate shared controls with keyboard, long text, errors, autofill, focus, and reduced motion before applying them everywhere. Preserve PDF fonts unless print changes are separately approved.

3. Build the mobile workspace

Use a compact top header with Documents and More actions. Use a labeled document-type select on phones rather than squeezing five segments into a row. Put number, date, and optional revision under Document details.

Below 1024px, show one active view: Edit or Preview. At 1024px and above, use two panes only when each remains readable. Keep one shared draft; changing the viewport must not reset it. Mobile content uses 16px padding and the spacing scale.

Render each item as a card: full-width description, quantity and unit price beneath, then amount and a labeled Remove action. Keep Add item visible at the list end. Use the compact row presentation only where it fits. Preserve suggestion pricing and discount handling.

Customer search uses a full-height phone sheet with search, results, empty/error states, and Add customer. Billing and shipping remain editable. Keep master-profile updates explicit and show the changes before saving.

Check: 1, 10, and 50 items; multiline descriptions; long customer names and addresses; tax override; free/paid delivery; discounts; all five document types.

4. Make actions and layers work on phones

Use a bottom action bar with total and Save. Reserve page space for its full height and safe-area inset. Keep focused fields visible when the software keyboard opens; do not cover the last item or error. Use dynamic viewport sizing and scroll containment for sheets only where needed. Preserve normal page scrolling and pinch zoom.

Use proper labels, decimal/tel/email keyboard hints, press feedback, and hover styles only for hover-capable pointers. Use accessible dialogs/sheets with focus containment, Escape/Close, focus return, and browser Back dismissing an open layer before leaving the editor. Essential actions never depend on hover or swipe.

Show saved/unsaved status. A disabled Download action explains that saving is required. Cancellation and recovery retain confirmation and existing storage behavior. Do not turn the existing soft-delete flow into permanent deletion.

Check: search with the keyboard open, sheet scrolling, Back, Escape, tab order, first-invalid-field focus, double taps, slow requests, failed requests, and retry.

5. Load PDF preview when it is useful

Mount the heavy viewer on demand for the phone Preview view. On desktop, load it as the second pane. Generate from the same draft mapping used for export and preserve scroll/draft state between views. Clearly label an unsaved preview.

Fit the preview to the available width with explicit zoom/open controls. Keep a native Open PDF/download fallback for mobile browsers that cannot render the embedded viewer. Avoid new PDF dependencies unless hardware testing proves the fallback insufficient.

Check: long multipage documents, company stamp, all five document types, shipping address on delivery orders, tax and delivery totals, cancelled documents, downloaded filenames, and iOS/Android opening behavior.

6. Verify and release in reviewable steps

Run TypeScript, lint, and a production build. Add focused regression tests for payload preservation, calculations, draft retention, Save locking, and component accessibility. Use controlled data; do not save test invoices into the live sheet without explicit authorization.

Review at 320/390/430px, tablet portrait/landscape, and 1280px desktop. Check 200% zoom and long content. Then test actual iPhone Safari and Android Chrome, including keyboard, notches, rotation, downloads, slow network, and failures.

Present the completed mobile and desktop flows for review before deployment. Local work and build success do not mean production has changed.

Assumptions and limits
  • Default to a light interface. Existing dark CSS tokens do not prove a complete dark-mode experience. Keep semantic tokens ready; a full theme switch is outside this plan.
  • Use in-memory drafts with explicit save and leave protection. Browser refresh recovery and local persistent drafts are separate features.
  • No dashboard, bottom navigation with invented destinations, offline write queue, customer database redesign, or automatic master-profile changes.
  • This review used source inspection, a 390px browser viewport, HTTP 200, and a read-only customer search. No real phone testing or invoice mutations were performed.
  • The plan does not depend on the removed Supabase or Telegram integrations.
